# Spanish and French (translation guide)

English is at `/`. Spanish is at `/es/` and French at `/fr/`, with translated URLs (`/es/calendario/`, `/fr/calendrier/`).
Every page has the same layout in all three languages; only the words change.

## How it is built
| What | Where |
| --- | --- |
| Languages, translated URL slugs, hreflang, `lp()` link helper | `src/i18n/index.ts` |
| Header, footer, breadcrumbs, forms, popover strings | `src/i18n/ui.ts` |
| AA glossary: popover definitions and the words that trigger them | `src/i18n/terms.ts` |
| Committee names in each language | `src/i18n/committees.ts` |
| Copy for each page (en, es, fr side by side) | `src/i18n/pages/*.ts` |
| District meeting lines (translated by pattern) | `src/i18n/districts.ts` |
| Page layouts shared by all three languages | `src/views/*.astro` |
| Spanish and French routes | `src/pages/[lang]/[...slug].astro` |
| Editor-made pages (CMS), translated copies | `src/content/pages-i18n/<es|fr>/<same-file-name>.yml` |

## Pages edited in the CMS (Site settings)
Home, Contribute, Resources, Literature, What is AA?, Registrar, Volunteer, Calendar and Services are edited in the CMS
under Site settings. An editor's English lives in `src/content/site/<page>.yml`; Spanish and French for each piece of
text come from, in this order:
1. **a fresh machine translation** in `src/content/site-i18n/<lang>/<page>.yml`, written by `scripts/translate.mjs`
   (run by the preview and "Translate recent changes" workflows, needs `DEEPL_AUTH_KEY`). Only text that is new or whose
   English changed is translated. Each record stores a hash of the English it came from and is used only while that hash
   still matches, so an old translation can never be shown for new English. To correct a translation by hand, edit its `t:`
   and leave `h:` alone; it is kept until the English changes again;
2. the translation already in `src/i18n/pages/<page>.ts` (used while the English is unchanged, and, if a text is edited
   but not yet translated, the old translation is kept rather than dropping to English);
3. the English itself.

The build prints `[i18n] <page> (<lang>): N text(s) changed in English ..., M not translated yet` when a page has text in
categories 2 (stale) or 3, so nobody has to remember to check. To translate by hand instead, run
`node scripts/translate.mjs --files src/content/site/home.yml` (or edit the files above).
Links, addresses and quotations (paragraphs starting `@en:`) are never translated. The Seventh Tradition text on the
Contribute page is machine translated like the rest; have it checked against AA's official wording before the page is
listed in `src/i18n/reviewed.json`.

**Extra sections.** Every one of those pages also has an "Extra sections" list at the bottom: editors add the same
blocks as on CMS pages (text, cards, callout, FAQ, buttons, ...). They are translated the same way; until translated they
show in English.

English pages are the files in `src/pages/`; each one just renders its view. Changing English copy means editing the
`en` block in `src/i18n/pages/<page>.ts`, then updating `es` and `fr` next to it (TypeScript flags a missing field).

## Why translated pages are hidden at first
Spanish and French pages are generated by an AI model, and AA wording matters. Until a bilingual AA member has read a
page it is served with `noindex`, left out of the sitemap, and left out of hreflang, so it cannot rank or embarrass anyone.
People who click the language menu can still read it.

**To publish a reviewed page:** add its English route key to `src/i18n/reviewed.json`, for example
`"es": ["", "contact", "committees/cpc"]` (`""` is the home page). Use `"es": "all"` when the whole language is reviewed.
The next build adds hreflang tags, the sitemap entries and the `llms.txt` links automatically.

## Rules for AA wording
1. **Never machine-translate canonical text.** The Preamble, Twelve Steps, Twelve Traditions, Twelve Concepts, the
   Serenity Prayer and Big Book or Twelve and Twelve quotations must be copied from the official Spanish and French
   editions on aa.org. Today the site contains no long canonical text. The Seventh Tradition appears in the
   contributions page and its glossary popover, and the Public Information policy statement, a Bill W. passage and Dr. Bob's 1950
   address appear on the Service page. Those are kept in English (marked `lang="en"`) until AAWS permission lets us use
   the official translations.
2. **Use the glossary** in `src/i18n/terms.ts` and `src/i18n/committees.ts` for every occurrence of a term.
3. **Keep anonymity and tone**: no medical claims, no "treatment" or "cure" language beyond what the English says.
4. Names, emails, Zoom IDs, passwords, addresses and URLs are never translated.

## Checks
```
npm run build
npm run check:i18n
```
`check:i18n` fails if a translated page is missing, has leftover English, has an unfilled `{placeholder}`, has the wrong
`<html lang>`, or links to a page that does not exist.

## Adding or changing content
- **A hand-built page**: edit `src/i18n/pages/<page>.ts` (all three languages), then build.
- **A CMS page** (like Get Involved): create `src/content/pages-i18n/es/<same-file-name>.yml` and the French twin, or use
  the *Páginas (español)* and *Pages (français)* collections in `/admin/`. The page's URL slug comes from the
  `segments` table in `src/i18n/index.ts` (add the Spanish and French slug there).
- **A new hand-built page**: add its slugs to `segments`, its key to `translatedKeys`, a view in `src/views/`, and an entry in
  `src/pages/[lang]/[...slug].astro`.
- **Events** made in the CMS are translated (above). They get Spanish and French pages at `/es/events/<name>/` and
  `/fr/events/<name>/`, and the home page and calendar lists show the translated title. These pages are always `noindex`.
  Events that come from the WordPress calendar are not translated.

## Automatic translation (free, DeepL)
When an editor changes English CMS content (a page in `src/content/pages/` or a committee in `src/content/committees/`),
the preview workflow drafts the Spanish and French and adds them to the same draft, so the reviewer sees them in the
pull request and in the preview.

| English | Translated copy |
| --- | --- |
| `src/content/pages/<name>.yml` | `src/content/pages-i18n/<es\|fr>/<name>.yml` |
| `src/content/committees/<slug>.yml` | `src/content/committees-i18n/<es\|fr>/<slug>.yml` |
| `src/content/events/<name>.md` | `src/content/events-i18n/<es\|fr>/<name>.md` (title, summary, image description, details) |

- **Free:** it uses DeepL API Free (500,000 characters a month, no charge; the plan stops at the limit rather than billing).
  Ordinary edits use a tiny fraction of that.
- **Safe:** it translates one piece of text at a time and puts it back in the same place, so structure, links, emails and
  settings cannot change. Links and emails are masked while translating and checked afterwards.
- **Published too early?** The preview workflow adds the translation to the draft about 15 seconds after the draft
  appears. If the draft is published before that, the translation arrives after the merge and is lost. The
  *Translate recent changes* workflow (`translate-catchup.yml`) catches this: after English content lands on `main`, it
  translates anything missing and opens a pull request for the owner to merge. It needs one setting: repo
  *Settings > Actions > General > Workflow permissions > Allow GitHub Actions to create and approve pull requests*. To
  translate a file by hand, run it from the Actions tab and give the English file name. Best practice is still to wait
  for the "Preview ready" comment before publishing.
- **Only what changed:** each translation records a hash of its English source (`sourceHash`). Unchanged files are skipped,
  and a hand edit by a bilingual reviewer is kept until the English changes again.
- **Still unreviewed:** machine translations stay hidden from search until listed in `src/i18n/reviewed.json`.
- **Not covered:** WordPress-calendar events, hand-built pages (`src/i18n/pages/*.ts`), district lines (translated by pattern) and the Spanish and
  French wording of AA's canonical texts (see the rules above).

### AA glossary
`glossary/aa-terms.tsv` tells DeepL how to translate AA's own terms (GSR, DCM, Area 30, the committee names, the Twelve
Steps and so on). It has three tab-separated columns (English, Spanish, French); open it in a spreadsheet or any editor.
It was drafted from `src/i18n/terms.ts`, `src/i18n/committees.ts` and the list above, so **a bilingual AA member should
confirm every row**. To add a term, add a row and merge; the next translation run uploads it.

- DeepL matches whole words, ignoring case, and adapts plural, gender and tense itself, so list the base form once.
- Skip ordinary words ("area", "service"): a glossary forces the term everywhere it appears. Phrases and AA names are ideal.
- It is uploaded as one multilingual glossary named `area30-aa-terms-<hash of the file>`. Unchanged file: nothing is
  uploaded. Changed file: the old glossary is replaced, so only one is ever kept.
- If DeepL refuses it (for example a plan that does not allow glossaries), the run says so and translates without it.
- Changing the glossary does not re-translate existing files; they update the next time their English changes. To redo
  one now, delete its `sourceHash` line (or the file) and run `npm run translate -- --files src/content/<kind>/<name>.yml`.
- Test the sync without DeepL: `node scripts/glossary.test.mjs`; the masking and markdown helpers: `node scripts/translate.test.mjs`.

**One-time setup:** create a free account at deepl.com/pro-api (choose *DeepL API Free*), copy the authentication key
(it ends in `:fx`), then add it as the repository secret `DEEPL_AUTH_KEY`. Without the secret the step is skipped and
nothing else changes.

**Run it by hand:**
```
DEEPL_AUTH_KEY=... npm run translate -- --base origin/main        # what this branch changed
DEEPL_AUTH_KEY=... npm run translate -- --all                      # everything whose English changed
npm run translate -- --base origin/main --dry-run                  # show what it would do, no key needed
```
